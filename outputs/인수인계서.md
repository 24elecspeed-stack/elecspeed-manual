## 1. 사용자 요청과 구현 방향

사용자는 기존 `tot.py`로 워드프레스에 올리던 전기수리 사례를 안드로이드 휴대폰에서 직접 입력해 등록하고 싶어 한다. 게시글은 기존 파이썬의 폼을 유지하는 것이 핵심 요구다. 이후 사이트 로그인 폼도 요청하여 별도 로그인 화면을 추가했다.

원본 APK를 수정한 것이 아니라, Java로 별도 Android 앱을 만들었다. 기존 APK의 사진 편집 기능 전체를 복제한 앱은 아니다. 현재 구현은 원본 게시글 형식의 일부를 재사용한 상태이며, 파이썬과 완전히 동일한 결과를 보장하지 않는다.

사용자가 최초에 적은 주소는 `24elecspee.com`이지만, 원본 파이썬의 설정에 따라 구현된 대상은 **https://24elecspeed.com** 이다. 주소 차이는 사용자에게 안내했다.

## 3. 현재 동작

### 로그인

1. 사이트 주소를 고정 표시한다. 앱에서 주소를 바꾸는 기능은 없다.
2. 워드프레스 사용자명과 **애플리케이션 비밀번호**를 입력한다.
3. 비밀번호 표시/숨기기를 선택할 수 있다.
4. Basic 인증으로 `GET /wp-json/wp/v2/users/me?context=edit`를 요청한다.
5. 이어서 `GET /wp-json/wp/v2/electric_case?context=edit&per_page=1&_fields=id`로 사례 접근을 확인한다.
6. 두 요청이 성공하면 계정 이름과 글 작성 화면을 표시한다.

일반 워드프레스 로그인 비밀번호나 웹 로그인 쿠키를 사용하는 방식이 아니다. 사례 조회 성공은 글 생성·공개 권한까지 보장하지 않는다. 로그인 실패 시 응답 오류를 표시하며 입력 내용을 다시 수정할 수 있다.

비밀번호는 SharedPreferences에 저장하지 않는다. 로그인 중에는 메모리의 입력 필드에 유지하며 로그아웃 때 지운다. 앱 프로세스가 다시 시작되면 재로그인해야 한다. 사용자명 기본값은 원본 설정의 `mymanowar`이며 수정 가능하다.

### 작성 및 등록

- 구/시, 동/읍/면, 제목, 본문을 직접 입력한다.
- 작업 유형을 선택하고 증상·원인·작업 내용을 입력한다.
- 지역·제목·본문은 필수 검사한다. 증상·원인·작업 내용은 빈 값도 전송한다.
- 빈 줄로 문단을 구분하고 `##`, `###`, `- ` 형식을 HTML로 변환한다.
- 원본 배너와 관련 태그를 붙여 WebView에서 미리 보여준다.
- 임시저장(`draft`) 또는 공개(`publish`)로 등록한다. 공개는 추가 확인 창을 거친다.
- 동일한 정규화 제목의 slug가 조회되면 등록을 중단한다. 기존 글을 덮어쓰지 않는다.
- 선택한 작업 유형의 taxonomy가 없으면 중단한다. 새 유형을 생성하지 않는다.
- 성공하면 결과 URL을 표시한다.
- 등록 버튼은 요청 중 비활성화한다. 등록 중에는 로그아웃을 막는다.
- 사용자명과 작성 내용, 선택한 작업 유형은 앱 내부 SharedPreferences `draft`에 저장한다.

화면 회전은 Activity의 `configChanges`로 처리한다. 백그라운드 요청은 일반 Thread이므로 프로세스 종료 후 요청 추적·복구는 제공하지 않는다.

## 4. 워드프레스 연동

| 항목 | 구현 |
|---|---|
| API 기준 주소 | `https://24elecspeed.com/wp-json/wp/v2/` |
| 글 등록 | `POST electric_case` |
| 중복 확인 | `GET electric_case?slug=...&context=edit&status=publish,draft,pending,future,private` |
| 작업 유형 조회 | `GET case_type?slug=...` |
| ACF | district, dong, symptom, cause, service |
| Yoast meta | _yoast_wpseo_title, _yoast_wpseo_metadesc, _yoast_wpseo_focuskw |
| 네트워크 | HTTPS, Basic 인증, 자동 리다이렉트 비활성화 |
| 시간 제한 | 연결 20초, 응답 읽기 45초 |

사이트에서 해당 커스텀 글 유형, taxonomy, ACF 및 Yoast 메타에 대한 REST 읽기·쓰기를 허용해야 한다. 실제 서버 응답과 필드 저장 여부는 아직 검증하지 않았다. 서버가 일부 필드를 무시하거나 권한 오류를 반환할 수 있으므로 첫 실기기 테스트는 임시저장으로 한다.

## 5. 원본 파이썬과의 차이

재사용 및 확인한 부분:

- 상단·중간·하단 배너 HTML은 원본 함수에서 추출했으며 파일 내용 일치를 검사했다.
- 문단 공통 스타일은 `BODY_PARAGRAPH_STYLE`을 옮겼다.
- 관련 태그의 알약 형태와 지역 태그 구조를 옮겼다.

아직 동일하지 않은 부분:

- 원본 `build_manual_post()`의 무작위 추가 문장·체크리스트·FAQ 생성은 포함하지 않는다.
- 중간 배너는 본문 중간에 한 번 배치한다. 원본 배치 알고리즘과 다르다.
- 배경 이미지는 원본 두 후보 중 한 장을 고정 사용한다.
- 공통 태그는 고정 목록이며 원본의 무작위 선택과 다르다.
- 제목 정리, 문단 분할, excerpt, SEO 설명 및 slug 생성은 간소화되어 있다.
- 대표이미지 생성·업로드·기존 로고 지정과 canonical 후속 갱신은 없다.
- 자동 예약 발행, 일괄 등록, 기존 글 수정 기능은 없다.
- 원본 APK의 사진 첨부·콜라주·썸네일 편집 기능은 없다.

사용자가 “py 폼 그대로”를 더 엄밀하게 요구하면 원본 `build_manual_post`, `insert_mid_banners`, `build_related_tags_html`, `build_wp_payload`와 결과 HTML을 비교하여 위 차이를 우선 조정한다.

## 6. 빌드 환경과 절차

현재 프로젝트는 **Gradle 프로젝트가 아니다.** 소스 ZIP을 Android Studio에서 바로 빌드할 구성 파일은 없다. 설치된 SDK 도구를 직접 실행하여 APK를 만들었다.

| 도구 | 확인한 위치 |
|---|---|
| Java/Javac/Keytool | `C:/Program Files/Android/Android Studio/jbr/bin` |
| Android build-tools | `C:/Users/manowar/AppData/Local/Android/Sdk/build-tools/36.0.0` |
| Android API jar 원본 | `C:/Users/manowar/AppData/Local/Android/Sdk/platforms/android-35/android.jar` |
| 작업용 API jar | `work/android/android.jar` |

빌드 순서:

1. `javac -encoding UTF-8 -source 8 -target 8 -classpath work/android/android.jar -d work/android/classes work/android/src/com/elecspeed/manual/MainActivity.java`
2. `java -cp <build-tools>/lib/d8.jar com.android.tools.r8.D8 --lib work/android/android.jar --min-api 26 --output work/android/dex <생성된 모든 class 파일>`
3. `aapt package -f -M work/android/AndroidManifest.xml -I work/android/android.jar -A work/android/assets -F work/android/base.apk`
4. ZIP 처리로 `work/android/dex/classes.dex`를 APK 루트의 `classes.dex`에 추가한다.
5. `zipalign -f 4 work/android/base.apk work/android/aligned.apk`
6. `apksigner.jar sign`으로 기존 서명 키를 사용하여 최종 APK를 출력한다.
7. `apksigner.jar verify --verbose` 및 `aapt dump badging`으로 검증한다.

기존 키 alias는 `manual`이다. 현재 키는 개발용이며 생성 시 사용한 저장소·키 암호는 모두 `android`다. 이 키로 서명된 앱을 업데이트하려면 같은 서명 키와 더 높은 versionCode가 필요하다. 운영 배포용 키 관리로 전환할 때는 기존 설치 앱의 업데이트 호환성을 검토한다. 키 자체는 소스 압축에 넣지 않았다.

### 빌드 중 확인한 환경 문제

- javac 25.0.2가 class 파일 생성 후 android.jar를 닫는 단계에서 `AccessDeniedException`을 출력했다. 따라서 javac 전체 실행이 정상 종료했다고 보고하면 안 된다.
- 생성된 최신 class 파일을 D8로 변환했으며 APK의 DEX에 `login`, `showLogin`, `showEditor` 메서드가 포함된 것을 확인했다.
- API jar를 디렉터리로 풀어 classpath로 사용하는 우회 시도는 패키지 탐색 오류로 실패했다. 현재 빌드는 jar classpath 결과를 사용했다.
- 다음 작업자는 정상적인 JDK/SDK 권한 환경에서 깨끗하게 다시 빌드하는 것이 좋다.

## 7. 검증 상태

완료:

- APK 생성 및 v2/v3 서명 검증 통과.
- 최신 APK의 package `com.elecspeed.manual`, versionName `1.1`, versionCode `2` 확인.
- minSdk 26(Android 8), targetSdk 35 확인.
- 매니페스트의 실행 Activity, INTERNET 권한, HTTPS 정책 확인.
- 원본 배너 HTML과 추출 파일 내용 일치 확인.
- DEX에 로그인 관련 메서드 포함 확인.

미완료:

- 실기기/에뮬레이터 설치 및 실행.
- 실제 로그인 성공·실패 동작, 로그아웃 후 재로그인.
- 실제 사례 등록, taxonomy/ACF/Yoast 저장 결과.
- 휴대폰 화면 크기별 폼·키보드·미리보기 레이아웃.
- 웹사이트의 실제 게시글 렌더링과 파이썬 결과 비교.

ADB가 `Cannot mkdir '\\.android': Permission denied` 오류로 실행되지 않아 기기 검증을 진행하지 못했다. 사이트 인증정보가 제공되지 않아 실제 로그인·업로드도 실행하지 않았다. 자동화된 기능 테스트는 작성하지 않았다.

## 8. 다음 작업자 점검 순서

1. 최신 APK를 기기에 설치하고 로그인 화면이 처음 표시되는지 확인한다.
2. 잘못된 비밀번호로 실패 안내와 버튼 복구를 확인한다.
3. 실제 애플리케이션 비밀번호로 로그인하고 작성 화면 진입을 확인한다.
4. 테스트 제목으로 임시저장한 뒤 관리자에서 HTML, ACF, taxonomy, SEO 값을 확인한다.
5. 같은 제목 재등록 차단과 로그아웃·재로그인, 작성 내용 보존을 확인한다.
6. 폰트, 화면 회전, 키보드, 긴 본문, 특수문자, 빈 필드를 점검한다.
7. 대표이미지 및 파이썬 폼의 미구현 차이를 사용자 요구에 맞춰 보완한다.

네트워크 시간 초과는 서버의 저장 실패를 뜻하지 않는다. 재시도 전 관리자 글 목록을 확인한다. 현재 slug 기반 중복 검사는 완전한 요청 중복 방지 장치가 아니며 동시에 두 기기에서 요청할 때의 경쟁 상태까지 막지 못한다.
